# 定时提醒功能设计方案

## 概述

为 WeStart（微信 AI 聊天助手）添加定时提醒能力，支持一次性延迟提醒和周期性 Cron 提醒，具备创建、查看、取消的完整生命周期管理。底层基于 Spring `TaskScheduler` + Redis 持久化，应用重启不丢失。

---

## 工具 API

### 1. `createReminder` — 一次性提醒

- **场景**：「10 分钟后提醒我喝水」「半小时后提醒我开会」
- **参数**：
  - `message` — 提醒消息正文，AI 用自然口吻编写（如「该喝水啦，起来活动一下吧💧」）
  - `delayMinutes` — 延迟分钟数，范围 1–1440（24 小时）
- **返回**：`已设置提醒，ID=abc123，10分钟后提醒：该喝水啦💧`
- **生命周期**：到达时间后触发一次，自动清理 Redis

### 2. `createRepeatingReminder` — 周期性提醒

- **场景**：「每天早上 9 点提醒我吃早餐」「每周一上午 10 点提醒我开会」
- **参数**：
  - `message` — 提醒消息正文
  - `cronExpression` — 六位 Cron 表达式（秒 分 时 日 月 周）
- **AI 内置常用模板**：
  - 每天早上 9 点 → `0 0 9 * * *`
  - 每周一上午 9 点 → `0 0 9 * * 1`
  - 每小时 → `0 0 * * * *`
- **返回**：`已设置周期性提醒，ID=abc456，频率：0 0 9 * * *，内容：吃早餐啦🍳`
- **生命周期**：按 Cron 表达式重复触发，直到手动取消或 Redis Key 被删除

### 3. `cancelReminder` — 取消提醒

- **场景**：「取消喝水的提醒」
- **参数**：`reminderId` — 创建提醒时返回的 ID，或通过 `listReminders` 查询得到
- **返回**：`已取消提醒：abc123`
- **实现**：从 `ConcurrentHashMap` 中取消 `ScheduledFuture`，并删除 Redis Key

### 4. `listReminders` — 查看所有提醒

- **场景**：「我还有哪些提醒？」（通常在取消前调用以获取 ID）
- **返回示例**：
  ```
  当前活跃的提醒：
  1. ID=abc123 [单次] 15:30 — 该喝水啦💧
  2. ID=abc456 [周期] 0 0 9 * * * — 吃早餐啦🍳
  ```

## 核心实现

### 数据模型

```java
private record ReminderTask(
    String id,              // UUID，唯一标识
    String userId,          // 微信用户 ID（from_user_id）
    String message,         // 提醒消息正文
    boolean recurring,      // true=周期性，false=一次性
    long fireTimeEpochMs,   // 一次性提醒触发时间戳（周期性为 0）
    String cronExpression   // 周期性 Cron 表达式（一次性为 null）
) {}
```

### Redis 存储

| 属性 | 一次性提醒 | 周期性提醒 |
|------|-----------|-----------|
| Key | `westart:reminder:{id}` | `westart:reminder:{id}` |
| Value | Gson JSON | Gson JSON |
| TTL | `delayMinutes + 5分钟缓冲` | 无 TTL（持久保留） |

### TaskScheduler 调度

| 类型 | 调度方式 | `ScheduledFuture` |
|------|---------|-------------------|
| 一次性 | `taskScheduler.schedule(runnable, Instant)` | 存入 `ConcurrentHashMap`，触发后移除 |
| 周期性 | `taskScheduler.schedule(runnable, CronTrigger)` | 存入 `ConcurrentHashMap`，取消时移除 |

### 取消流程

```
cancelReminder(reminderId)
  → scheduledFutures.remove(reminderId) → future.cancel(false)  // 停止调度
  → redisTemplate.delete(key)                                    // 清理 Redis
  → 返回 true/false
```

### 启动恢复

`@EventListener(ApplicationReadyEvent.class)` → `reloadOnStartup()`
1. 扫描 Redis `westart:reminder:*` 所有 Key
2. 对每个 Key → `loadTask(key)` 反序列化
3. 周期性：重新注册 `CronTrigger` 调度
4. 一次性：已过期则删除，未过期则重新注册 `Instant` 调度

## 关键技术决策

| 决策 | 理由 |
|------|------|
| `TaskScheduler` 而非 `@Scheduled` | 需要运行时动态注册/取消任务 |
| Redis 持久化而非纯内存 | 应用重启不丢失提醒 |
| Cron 表达式由 AI 生成 | 自然语言→Cron 映射简单，`@Tool` description 内置模板 |
| 一次性提醒设 Redis TTL | 自动兜底清理，避免僵尸 Key |
| 周期性提醒不设 Redis TTL | 需持续保留，手动取消时删除 |
| `@ToolMemoryId` 注入 userId | 复用框架机制，无需 ThreadLocal |
| `sessionRegistry.findClientByUserId()` | 定时触发时动态查找 iLink 客户端发微信 |

## 用户交互示例

### 场景 1：一次性提醒
```
用户：10分钟后提醒我喝水
AI：  好的，已设置提醒，10分钟后通知你 💧

（10 分钟后）
微信：⏰ 该喝水啦，起来活动一下吧💧
```

### 场景 2：周期性提醒
```
用户：每天早上 9 点提醒我吃早餐
AI：  已设置每天早上 9 点的提醒，ID=abc456 🍳

（每天 9:00）
微信：⏰ 早上好，该吃早餐啦🍳
```

### 场景 3：取消提醒
```
用户：取消喝水的提醒
AI：  [调用 listReminders] 你当前有 2 个提醒：
     1. abc123 [单次] 15:30 — 该喝水啦💧
     2. abc456 [周期] 0 0 9 * * * — 吃早餐啦🍳
     你想取消哪个？
用户：第一个
AI：  [调用 cancelReminder("abc123")] 已取消 💧
```

## 后续扩展方向

- **免 Cron 的自然语言解析**：AI 传「每天早上 9 点」而不是 Cron 表达式，服务端解析为 Cron
- **提醒静默期**：夜间不发送提醒
- **提醒确认机制**：用户回复「已完成」标记提醒处理
- **Web 管理面板**：前端页面可视化查看和取消提醒
