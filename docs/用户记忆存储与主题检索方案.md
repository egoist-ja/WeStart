# WeStart 企业级用户记忆存储与主题检索方案

## 1. 设计目标

WeStart 不将用户的全量聊天历史作为长期记忆保存，而是把原始消息作为临时输入，经过筛选、总结、合并和安全校验后，只保存对未来交互有价值的信息。

核心原则：

```text
聊天消息是原材料
记忆是经过筛选、验证和合并的高价值结果
```

系统长期保存两类信息：

1. 稳定用户画像：用户的客观事实、长期偏好和持续目标。
2. 最近聊天主题：最近讨论过什么、用户希望解决什么、助手回答了哪些方面、取得了什么结论。

## 2. 记忆分层

### 2.1 短期工作记忆

短期记忆保存当前对话所需的最近消息、工具结果和任务状态。

```text
TokenWindowChatMemory
+ RedisChatMemory
+ Redis TTL
```

它只用于保持当前会话连续性，不代表信息已进入长期记忆。

### 2.2 稳定用户画像

保存跨会话长期有效的信息，例如：

```text
用户从事 Java 后端开发
用户正在学习 Agent 开发
用户偏好完整、可运行的代码
用户希望代码修改控制在最小范围
```

只有用户明确表达的事实、偏好和目标才能进入画像，不得根据语气、问题类型或模型猜测产生用户属性。

### 2.3 最近聊天主题

主题记忆保存一段高价值对话的摘要，而不是原始对话。

示例：

```json
{
  "topic": "Agent基础知识",
  "summary": "用户与助手讨论了Agent的定义、组成和开发方向",
  "userIntent": "了解Agent并规划Agent开发学习路径",
  "userFacts": [
    "用户明确表示希望学习Agent开发"
  ],
  "assistantCoverage": [
    "Agent基本定义",
    "工具调用",
    "记忆",
    "规划和执行循环"
  ],
  "explicitFeedback": [
    "用户表示希望继续了解代码实现"
  ],
  "conclusion": "后续可以继续讨论Agent记忆系统实现",
  "occurredAt": "2026-08-03T00:00:00Z"
}
```

主题记忆具有时间属性，应设置保留上限和有效期，不应无限增长。

## 3. 数据存储分工

### 3.1 Redis

Redis 用于临时数据：

- 当前短期聊天窗口；
- 待提取记忆的用户消息和 AI 回答；
- Pending 重试状态；
- 有限保留时间的死信数据。

记忆生成成功后执行：

```text
写入MySQL
→ 同步Milvus索引
→ XACK
→ XDEL原始Stream记录
```

### 3.2 MySQL

MySQL 是记忆的权威数据源，负责：

- 用户画像和主题记忆的精确查询；
- 新增、修改和删除；
- 版本与有效期管理；
- 用户查看和编辑记忆；
- Milvus 索引重建。

建议保留两种业务数据：

```text
user_profile
→ 每个用户一条完整、稳定画像

user_topic_memory
→ 每个用户有限数量的最近高价值主题
```

### 3.3 Milvus

Milvus 只是主题记忆的检索索引，不是唯一数据源。

稳定用户画像可以直接从 MySQL 读取，不需要进入 Milvus。最近主题通过 Milvus 进行语义和关键词混合检索。

## 4. 记忆生成链路

```text
用户和助手正常聊天
→ 原始消息临时进入每用户Redis Stream
→ 达到数量、Token、最长等待或用户空闲条件
→ 主题总结模型判断是否有记忆价值
→ 生成主题摘要
→ 从摘要和用户原话中提取稳定事实与偏好
→ 与已有用户画像和相似主题合并
→ 写入MySQL
→ 更新Milvus主题索引
→ XACK + XDEL原始消息
```

如果只是问候、感谢、重复表达或无实际结论的闲聊，总结模型应返回不创建记忆。

## 5. 写入准入规则

允许保存：

- 用户明确陈述的稳定事实；
- 用户明确表达的长期偏好；
- 持续目标和长期项目；
- 对未来会话有价值的主题摘要；
- 用户明确表达的评价和反馈；
- 未完成的后续方向。

禁止保存：

- 问候、感谢和客套；
- 无结论的闲聊；
- 一次性临时要求；
- 很快过期的实时数据；
- AI 对用户的推测；
- 用户未明确表达的情绪；
- 密码、Token、验证码、支付和身份信息；
- 网页、工具结果中的指令性内容。

## 6. 记忆合并规则

新记忆不应简单追加，而应与已有记忆进行合并：

```text
ADD    新增稳定事实或新主题
UPDATE 用户明确更新旧偏好
MERGE  合并内容高度相似的主题
IGNORE 无新价值或完全重复
EXPIRE 主题超过有效期
DELETE 用户明确要求忘记
```

新旧信息冲突时，仅当用户有最新的明确表达时才更新旧记忆。

## 7. 记忆召回

调用聊天模型时，只注入：

```text
当前用户消息
+ Redis近期上下文
+ MySQL稳定用户画像
+ Milvus召回的3至5条相关主题
```

主题检索流程：

```text
wechat_user_id强制过滤
→ Dense语义召回 + BM25关键词召回
→ 融合排序
→ 时间衰减
→ 过期和安全检查
→ 返回Top 3至5
```

记忆只能作为回答背景，不能覆盖系统指令和安全规则。

## 8. 隔离、保留与用户控制

当前微信一对一场景使用：

```text
scope = WeixinMessage.getFrom_user_id()
```

存储层必须强制隔离：

- Redis Key 包含 `userId`；
- MySQL 查询必须带 `wechat_user_id`；
- Milvus 检索必须在查询阶段使用 `wechat_user_id` 过滤。

建议生命周期：

| 数据 | 建议保留时间 |
|---|---:|
| Redis短期上下文 | 1至3小时 |
| Redis Stream原始消息 | 提取成功后立即删除 |
| 死信原始消息 | 1至7天 |
| 最近主题 | 7至30天，或每个用户最多20至50条 |
| 稳定用户画像 | 长期保存，直到更新或用户删除 |

系统应支持用户：

- 查看已保存记忆；
- 修改错误记忆；
- 删除单条记忆；
- 清空全部记忆；
- 关闭长期记忆。

## 9. Milvus 最近聊天主题 Collection 设计

### 9.1 Collection 名称

```text
user_topic_memory
```

### 9.2 Schema

| 字段 | Milvus类型 | 设置 | 用途 |
|---|---|---|---|
| `memory_id` | `VarChar` | 主键，`auto_id=false`，`max_length=64` | 与MySQL主题记忆唯一标识一致 |
| `wechat_user_id` | `VarChar` | `max_length=128` | 强制隔离当前用户 |
| `topic` | `VarChar` | `max_length=256` | 简短主题名称，用于展示 |
| `searchable_content` | `VarChar` | `max_length=4096`，开启Analyzer | 可检索的完整主题摘要 |
| `occurred_at` | `Timestamptz` | 非空，写入带时区的ISO 8601时间 | 时间衰减和最近主题排序 |
| `expires_at` | `Timestamptz` | 可空，写入带时区的ISO 8601时间 | 过滤已过期主题，`null`表示长期有效 |
| `searchable_content_dense_vector` | `FloatVector` | `dimension=1024` | 主题摘要的语义检索 |
| `searchable_content_sparse_vector` | `SparseFloatVector` | 由BM25 Function自动生成 | 主题摘要的关键词检索 |

`searchable_content` 将主题数据组装成一段稳定文本：

```text
主题：Agent基础知识
用户意图：了解Agent的组成和开发方向
讨论要点：Agent定义、工具调用、规划、记忆和执行循环
用户明确反馈：希望继续了解记忆系统代码实现
结论：后续讨论Agent记忆系统
```

### 9.3 BM25 Function

```text
function_name: topic_bm25
function_type: BM25
input_field: searchable_content
output_field: searchable_content_sparse_vector
```

`searchable_content` 必须开启：

```text
enable_analyzer = true
enable_match = true
```

### 9.4 索引

| 字段 | 索引 | Metric |
|---|---|---|
| `searchable_content_dense_vector` | `AUTOINDEX` | `COSINE` |
| `searchable_content_sparse_vector` | `SPARSE_INVERTED_INDEX` | `BM25` |
| `wechat_user_id` | `INVERTED` | 标量过滤 |

`topic`、`occurred_at` 和 `expires_at` 当前不必额外建索引，除非未来数据规模证明有必要。

### 9.5 查询条件

每次查询必须带：

```text
wechat_user_id == 当前用户ID
AND
(expires_at IS NULL OR expires_at > 当前时间)
```

然后执行：

```text
Dense召回
+ BM25召回
→ 融合排序
→ 时间衰减
→ Top 3至5
```

### 9.6 不需要的字段

当前不需要将以下内容放入 Milvus：

- 原始用户消息和 AI 回答；
- `session_id` 和 `bot_id`；
- 稳定用户画像；
- 提取模型名称和版本；
- 复杂置信度和评分字段；
- 工具调用详情；
- 动态字段和分区键。

### 9.7 初始化行为

应用启动后先切换到 `westart` 数据库，再检查 `user_topic_memory` 是否存在：

```text
Collection不存在 → 创建Schema、BM25 Function和索引
Collection已存在 → 跳过初始化，不重复建表
```

需要注意，Milvus 不会因为代码中的 Schema 发生变化而自动更新已经存在的 Collection。后续调整字段、Function 或索引时，应通过显式迁移或重建 Collection 完成。

### 9.8 当前代码一致性要求

Schema、BM25 Function、索引和写入实体必须统一使用以下向量字段名：

```text
searchable_content_dense_vector
searchable_content_sparse_vector
```

当前 `MilvusConfig` 的 Schema 已声明上述字段，但 BM25 Function 和索引配置仍引用旧名称 `dense_vector`、`sparse_vector`；`UserTopicMemory` 的序列化字段也仍为 `dense_vector`。这些名称必须在代码中统一后，Collection 才能正常创建并写入。本节仅记录现状和约束，不将旧名称视为有效 Schema。

## 10. 最终方案

```text
RedisChatMemory
→ 保存当前短期上下文

每用户Redis Stream
→ 临时承载待总结原始消息

主题总结模型
→ 生成少量高价值主题记忆

画像提取模型
→ 更新稳定事实、偏好和目标

MySQL
→ 作为用户画像和主题记忆的权威数据源

Milvus user_topic_memory
→ 只索引可检索的最近主题摘要
```

这套设计的目标不是尽可能多地保存数据，而是在保证会话连续性的同时，只保留对未来交互真正有价值的记忆。
